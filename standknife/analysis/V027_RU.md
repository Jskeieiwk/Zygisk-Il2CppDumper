- Цена кадра упала: `cameraMs` 6.6–9.8 (было 12–16), `canvasMs` 4–6 (было 9–12), `gameFps` 33–48 (было 26–40).

- Прочее без изменений: `captureMs` макс 20–70 мс (редкие всплески), пары `fire-hooks-suspended/active`.

## Что сделано

**Кадр передаётся без вызовов Java.** JS упаковывает примитивы в целые числа и пишет их прямо в память прямого
`ByteBuffer`, которым владеет `CanvasBatch`. Java читает свежий кадр на UI-потоке в каждом vsync (`Choreographer`) и рисует
его сразу в `onDraw`. Это убирает вызов моста (≈3.5 мс) и стоимость `Picture`, а ESP рисуется по самым свежим данным на момент
vsync, без очереди из устаревших кадров.

- Адрес буфера: `Java.vm.getEnv().getDirectBufferAddress(...)` из `frida-java-bridge` (есть в проекте).
- Перед использованием адрес проверяется: он должен лежать в читаемом и записываемом диапазоне нужного размера, и слово,
  записанное из JS, должно читаться в Java (`CLOUD:shared-frame=on`). Иначе пишется
  `CLOUD:shared-frame-unavailable ...` и работает прежний путь v0.26 с одним вызовом `frame()`.
- Протокол: слово последовательности (чётное, пишется последним), маркер `последовательность ^ 0x5EED5EED`,
  длина, время записи, затем данные. Java копирует данные во вспомогательный массив и принимает кадр только если
  последовательность не менялась и маркер совпал, иначе остаётся прежний кадр. Нечётная последовательность, рваный кадр,
  нелепая длина, неизвестный вид примитива и обрезанный примитив безопасно игнорируются (тест нашёл ошибку, при которой
  рваный кадр портил предыдущий; исправлено).
- Геометрия поверхности игры считается в Java каждый vsync и публикуется скрипту в той же памяти, поэтому JS её больше не
  опрашивает через мост.
- Задержка в `lagAvgMs/lagMaxMs` теперь считается от записи кадра в JS до его отрисовки.
- Чистка экрана (смена сцены, ошибка рендера) — пустой кадр через ту же память.

Телеметрия: `CLOUD:native-picture ... renderMs=.. packMs=.. writeMs=.. transport=shared-memory`. Если строка
говорит `transport=call`, значит общая память не включилась, и причина в `CLOUD:shared-frame-unavailable`.

## Проверки

- 26 из 26 тестов. Новые: `shared-frame.cjs` (упаковщик, порядок записи: последовательность последней, чтение
  геометрии, враждебные значения), `shared-protocol.cjs` (**настоящий JS-упаковщик пишет образ буфера, настоящий
  `CanvasBatch` читает и рисует; результат сравнивается дословно, включая кавычки, запятые, кириллицу и суррогатную пару;
  геометрию Java читает настоящий JS-код**), расширенный `native-picture.cjs` (последовательности, рваные кадры,
  истечение, задержка, цикл vsync), `overlay-frame.cjs` (ни одного вызова overlay на кадр в режиме общей памяти).
- Мутации (перепутанные x/y в упаковщике, неверный маркер) сквозной тест ловит.

## Не проверено

- Что на устройстве адрес прямого буфера проходит проверку диапазона и самотест (иначе будет откат на v0.26 с записью причины).
- Реальный FPS, задержка и цена одного кадра на телефоне. Кадр теперь декодируется и рисуется на UI-потоке в `onDraw`;
  его длительность видна в `avgMs/maxMs` строки `native-picture`.
- Порядок записей между потоками без явных барьеров на ARM: защита построена на маркере и проверке последовательности,
  худший случай — один пропущенный кадр.
