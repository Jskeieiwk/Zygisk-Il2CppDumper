# v0.23: Java Picture presentation

v0.22 telemetry still reports Canvas averages up to 143 ms, maxima 278 ms.
The new 72-second recording shows sampled Cloud readings around 25–49 FPS.
The compiled batch helper alone did not establish improved performance.

The compiled CanvasBatch now also extends Android View. Its onDraw runs in
Java and displays an immutable Picture without entering Frida JS. The game
camera callback records the next Picture using the existing complete drawing
path (including avatars and effects), then publishes it. Only the latest
Picture is retained; frames expire after 350 ms or are cleared on session reset.
The recording canvas is never mutated after publication.

Log CLOUD:esp-renderer=native-picture confirms selection of this path.
CLOUD:native-picture reports Java presentation statistics separately. Legacy
canvasMs now measures Picture composition in this path; it is included in the
camera callback time, so these durations must not be added together. Composition
still uses JS and some Java bridge calls, and may itself be costly. No claim
of measured performance improvement is possible without a device run.

Fallback remains the JS View when dex loading/creation fails. Frame recording
failures clear the picture and report CLOUD:picture-frame-error. Tests cover
latest-frame replacement, expiry, clearing and stats with Android API stubs;
they cannot validate Android GPU playback, dex class loading or real FPS.
