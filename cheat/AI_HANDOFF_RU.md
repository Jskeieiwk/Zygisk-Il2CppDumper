На устройстве НЕ проверено. Подтверждены только сборка/распаковка/host tests.

Аим для FPHitscan автоматически читает HitscanWeaponConfig.get_BulletSpeed, BallisticProfile.zoT (gravity, реальная загрузка +0x10) и zoJ (airDrag, +0x14). zoz читает underwaterDrag +0x18 и для gravity НЕ используется. native/ballistics.h воспроизводит воздушную ветку BallisticIntegrator.Step RVA 0xd909d2c: dt=1/32, gravity умножается на Vector3.down (static field +0x24), drag clamp, затем усреднение старой/новой скорости; engine сохраняет именно среднюю скорость. Численный поиск ищет раннее достижимое решение не дальше 8 секунд. Движение цели оценивается по мировым координатам головы между кадрами (50 мс при aim), независимо от vehicleID/типа транспорта. Телепорты/разрывы истории отбрасываются, записи старше 2 секунд удаляются. Для неизвестного оружия/профиля/недостижимой цели аим не выдаёт фиктивное решение; пишет предупреждение. Нет решения для луков, ракет, подводной стрельбы, резких будущих манёвров; server latency и carrier velocity стрелка не компенсируются. Проверка видимости пока остаётся прямой линией к текущей голове, а не трассировкой всей дуги. Это не 100% попадания по машине/коптеру.

CrosshairManager.Update RVA 0x7a71074 (первая инструкция 0xf81d0ffe) hook после оригинала подавляет только GameObject компонентов CrosshairData.m_Image/+0x40 и m_Crosshair/+0x58 у default/current/custom crosshairs. Исходные activeSelf сохраняются, объекты удерживаются GC handles, при выключении восстанавливаются. Hit markers и менеджер HUD не отключаются. Overlay рисуется только когда suppression hook установлен. Визуалы: toggle замены прицела, 4 формы (cross/dot/circle/cross+dot), RGB-палитра, размер, зазор, толщина. Сохранение через prefs/профили как раньше. JNI configure расширен до 54 ints; новый crosshairAvailable, всего 13 зарегистрированных native методов.

Проверки: native API25/ARM64 и Java/DEX; --verify; 25 runtime fingerprints; host tests stationary/transverse/elevating/approaching targets, unreachable and invalid inputs; аналитические проверки времени перехвата и шага интегратора; config on/off и согласованность JNI. Android suppression/restore, цель в транспорте и фактические попадания ещё не проверены.

Пользователь подтвердил появление меню r09 после force-stop. Затем две попытки завершились SIGABRT на UnityMain через 13 секунд uptime. Одинаковый стек: abort <- 0x6293ee0 <- 0x628c1d8 <- 0x628bb0c <- 0x628b7ac <- 0x6293100 <- 0x61e7300 <- 0x6245ac0 <- 0x61efd1c. Точный причинный механизм по одному стеку не доказан; ранняя работа с runtime из незарегистрированного pthread является конкретным дефектом r09.

Он проверяет Build ID, запускает UI и устанавливает PlayerManager.LateUpdate hook. initializeFromUpdate вызывается после originalUpdate, использует уже зарегистрированный managed поток; attach/detach не вызываются, чтобы не отсоединять engine-owned thread. Не более 10 попыток разрешения с паузой 1 секунда между ними. Методы сбрасываются перед повторной попыткой; на успехе устанавливаются дополнительные hooks и публикуется ready. Состояние загрузки UI отделено от готовности runtime. Логи включают tid и первый world sample.

Проверено: ARM64 API25 сборка с -Werror для собственного кода, Java/DEX, --verify распаковки, синтаксис shell, 25 runtime fingerprints и покрытие BIND. # Передача проекта Oxide 12034

## Состояние — читать первым
Это незавершённый проект, НЕ рабочий чит. Наличие интерфейса и успешная компиляция не подтверждают игровые функции. Старый STATUS.md описывает написанный код слишком оптимистично; этот файл имеет приоритет как отчёт о фактическом состоянии.

Пользователь проверил r07: меню открывается по счётчику игроков/ботов. JavaVM была недоступна через обычные dlsym/dlopen; запасной поиск JNI_GetCreatedJavaVMs по ELF уже загруженной libart.so позволил показать UI. r08 уменьшает меню 540×330 -> 440×270 dp, шрифты и счётчик. Размер r08 на телефоне ещё не подтверждён.

ESP, аим, счётчики и другие функции НЕ подтверждены и в последних проверках не работали: runtime не инициализируется. В предоставленной libil2cpp.so нет стандартных экспортов il2cpp_*. dlopen RTLD_NOLOAD также не получает дескриптор из контекста загруженного модуля. Поэтому основная resolve() изначально не могла работать.

## Состав архива
- project/: текущие C++/Java исходники, shell launcher, скрипты сборки, анализ.

## Runtime adapter — незавершённая разработка
native/runtime_12034.h содержит адреса части функций и проверки первых инструкций, только под данный Build ID. Код компилируется, но после добавления адаптера на устройстве НЕ запускался. Не считать найденные адреса, структуры и сигнатуры валидированными одним фактом компиляции.
Найдены обёртки domain/thread/string/unbox/image name/class methods/method name. Добавлены внутренние method_get_param_count (0x6237d88) и method_get_param (0x6237d90), поиск методов по имени и количеству аргументов (пока без обхода родителей), перечисление сборок через getter vector 0x6222468, assembly_get_image с проверкой обратной ссылки image+0x10. Эти части требуют независимого ревью и тестирования.
Отсутствуют как минимум class_from_name, class_get_type, type_get_object, runtime_invoke, string_new, GC handles и часть object/type операций. Перечень зависимостей находится в Api и resolve() в oxide_features.cpp.
mono_class_get_checked по адресу 0x61f111c — заглушка, возвращающая null. Нельзя просто переименовать все il2cpp_* в mono_*: сигнатуры различаются (пример mono_string_new переносит x1 в x0).
analysis/runtime-12034.json и mono-exports.txt — заметки, не доказательство корректности.
